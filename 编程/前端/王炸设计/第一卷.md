# 消息已读

IM 应用中，我们修改<u>单个</u>消息的已读状态，很喜欢循环遍历消息列表, 修改对应的消息 read 状态。时间复杂度是O(N)。

但如果我们用一个 `Set`（或者 Map）存所有已读的 `id`，单点已读是 O(1)。

处理全部已读的时候，可以引入“**时间游标 (Cursor / Watermark)**”机制。增加**最后一次“全部已读”的时间戳**，存储在后端数据库中。

# 请求共享与防重复

你的页面里有 3 个不同的组件（比如头部导航、侧边栏、个人中心），它们都需要获取“当前用户的详细信息”。

``` ts
class UserService {
  // 🏆 Promise 缓存池
  private fetchUserPromise: Promise<UserInfo> | null = null;

  getUserInfo(): Promise<UserInfo> {
    // 1. 如果当前已经有一个正在路上的请求，直接把这个 Promise “拼车”返回给它！
    if (this.fetchUserPromise) {
      return this.fetchUserPromise; 
    }

    // 2. 如果没有，就真正发起网络请求，并把这趟“班车”存起来
    this.fetchUserPromise = api.get('/user/info')
      .then(res => {
        return res.data;
      })
      .finally(() => {
        // 3. 请求结束（无论成功失败），把班车销毁。下次调用就会发新请求。
        this.fetchUserPromise = null; 
      });

    return this.fetchUserPromise;
  }
}
```

# 幂等性主权转移

- **菜鸟做法：** 结账时防止用户连点两次按钮导致付两次钱，用 `isLoading` 禁用按钮。但如果网络断了，按钮卡死。
    
- **过瘾技巧：** 前端在组件挂载时，生成一个唯一的 UUID（幂等键），放在 Request Header 里发给后端。就算用户狂点 10 次发了 10 个请求，后端根据 UUID 识别为同一次操作，只扣一次钱。彻底根除重复提交

#### 场景 1：高并发抢购 / 领券秒杀系统

- **痛点：** 抢茅台或者抢满减券。用户在倒计时结束的一瞬间，因为焦躁，会以每秒 10 次的手速疯狂点击“抢购”按钮。如果你只用 `btn-disabled`，万一浏览器卡了没置灰，或者请求超时了，就会发出去一堆烂请求。
    
- **主权落地：** 弹窗打开或页面初始化时，前端立刻生成一个全局唯一的 `Coupon-Claim-Token (UUID)`。用户狂点 10 次，发出的 10 个请求 Header 里带的都是同一个 Token。
    
- **后端配合：** 后端网关层的 Redis 接到请求，直接用这个 Token 做 `SETNX`（互斥锁）。后面的 9 个请求根本连后端的业务代码都进不去，直接被网关挡回。绝对安全，极其高效。
    

#### 场景 2：UGC 巨型表单发布 (如长篇图文、低代码搭建保存)

- **痛点：** 用户写了 3000 字的文章，配了 10 张图。点击“发布”，如果用户坐在高铁上，网络极不稳定，请求发出去 10 秒没响应（其实后端已经存库了，但前端没收到回包）。前端超时机制触发了“自动重试（Auto Retry）”。
    
- **悲剧后果：** 数据库里出现了两篇一模一样的 3000 字文章。
    
- **主权落地：** 前端在用户新建草稿时生成 `Draft_ID`，或在点击发布瞬间生成 `Action_UUID`。底层 Axios 拦截器里的“失败重试插件（axios-retry）”带着这个 UUID 去重试。后端识别到 UUID 一致，直接丢弃写库操作，但**返回 HTTP 200 成功响应**。
    

#### 场景 3：BFF 层 (Backend For Frontend) 的微服务防抖

- **痛点：** 现在前端经常会写 Node.js BFF 层（比如 GraphQL 服务）。前端调 BFF，BFF 去调底层的 Java/Go 微服务。
    
- **主权落地：** 浏览器发请求给 BFF 时带上 `x-idempotency-key`。BFF 如果因为超时去重试底层的 Java 接口，必须把这个 Key 原封不动地透传给 Java。这样，一条业务链路无论在哪个环节发生重试，底层数据库都能保证“Exactly-Once（精确执行一次）”的语义。

# 意图预加载
预加载的本质是**“用客户端的微小流量带宽，去换取 P99 分位绝对的 0 延迟体验”**。但如果全站滥用，会导致服务器被 DDoS 攻击一样打挂。所以它必须用在“高确定性、高价值”的场景。

#### 场景 1：复杂表格的“侧边抽屉/详情弹窗” (B端中后台/SaaS)

- **痛点：** 用户在看一个有 100 行数据的复杂表格。点击“查看详情”，右侧划出一个抽屉面板。但抽屉里的数据往往需要调用极其沉重的多表联查 API，Loading 圈要转 1-2 秒，业务方抱怨系统卡。
    
- **预加载落地：** 当用户的鼠标 `mouseenter` 到“查看详情”按钮，且**停留超过 100ms**（过滤掉无意划过），立刻触发请求。因为抽屉的 CSS 划出动画通常需要 300ms，加上人类点击的 200ms 反应时间。这 500ms 的时间差，足够让 API 带着数据回来。
    
- **用户体感：** 抽屉滑出的瞬间，数据仿佛原本就在那里，没有一丝等待。
    

#### 场景 2：电商/SaaS 的“超级大菜单” (Mega Menu)

- **痛点：** 像淘宝首页或者阿里云控制台左侧的导航栏。鼠标放上去，会弹出一个极其庞大的二级/三级菜单，里面甚至包含个性化的推荐商品和运营 Banner。这些数据强依赖实时接口。
    
- **预加载落地：** 用户的鼠标刚进入一级菜单的感应区，立刻发请求获取树状目录结构。
    
- **架构师防坑设计：** 配合 `LRU Cache`（最近最少使用缓存）。如果用户在菜单里反复横跳，不能重复发请求；同时配合 `AbortController`，如果用户鼠标 50ms 内移出，立刻砍掉还没发出的请求，放过服务器。
    

#### 场景 3：分页与无限滚动 (Pagination / Infinite Scroll)

- **传统做法：** 滚到底部 -> 触发 `onLoadMore` -> 菊花转圈 -> 渲染。
    
- **预加载落地 (Intersection Observer 结合)：** 在列表倒数第 5 个元素（或者距离底部还有 200% 视口高度时）埋下一个隐形的哨兵节点。一旦哨兵进入视口，立刻静默请求下一页数据存入内存（不渲染）。
    
- **用户体感：** 用户仿佛在刷一个永远刷不到底的列表，永远看不到 Loading。

# 向 V8 引擎宣战 —— 对象池与零 GC 架构 (Zero-GC Object Pooling)

**业务场景：** 开发高频交易 K 线图、Web 弹幕引擎、或者类似 Figma 的万节点渲染。每秒钟有成千上万的数据在不断产生和销毁。

- **菜鸟做法：** 在 `requestAnimationFrame` 的高频循环里，不断地 `const node = { x, y }` 或者 `new Point(x,y)`。
    
- **致命瓶颈：** 内存飙升！由于你疯狂创建新对象，V8 引擎的“垃圾回收器 (Garbage Collector, GC)”会被频繁唤醒。**GC 运行时，会触发 "Stop-The-World"（全停顿）**。此时就算你代码写得再好，整个浏览器主线程也会被强行冻结 50-100ms。用户的直观感受就是：画面每隔两秒就诡异地“卡抽”一下。
    
- **首席的降维打击（对象池）：** 在应用初始化时，我一口气 `new` 出 10000 个空对象放进一个数组（或者使用连续内存的 `ArrayBuffer`）。 当需要新节点时，我不去 `new`，而是去池子里**“借”**一个已经被标记为闲置的对象，重置它的 `x, y` 属性。当节点被销毁时，我不 `delete` 它，只是把它放回池子里标记为闲置。
    
- **核弹级效果：** 整个应用运行期间，**内存分配为 0，垃圾回收触发次数为 0。** 彻底跨越浏览器的极限，实现像 C++ 般稳定死守 60fps/120fps 的丝滑渲染。

```ts
// 纯逻辑演示：千万级渲染的底层内存池
interface IPoint { x: number; y: number; active: boolean; }

class ZeroGCPool {
  private pool: IPoint[];
  private freeIndices: number[]; // 记录哪些索引是空闲的

  constructor(poolSize: number = 10000) {
    // 💡 降维打击 1：初始化时一次性向系统申请连续内存
    // 之后程序的整个生命周期，再也不会触发内存分配！
    this.pool = Array.from({ length: poolSize }, () => ({ x: 0, y: 0, active: false }));
    
    // 一开始所有坑位都是空闲的
    this.freeIndices = Array.from({ length: poolSize }, (_, i) => i);
  }

  // 替代 `new Point(x, y)`
  spawn(x: number, y: number): IPoint | null {
    if (this.freeIndices.length === 0) return null; // 池子满了
    
    // 💡 降维打击 2：从池子里“借”一个对象，只修改属性，不分配新内存！
    const index = this.freeIndices.pop()!;
    const node = this.pool[index];
    node.x = x;
    node.y = y;
    node.active = true;
    return node;
  }

  // 替代 `delete node` 或设为 null 等待 GC
  kill(nodeIndex: number) {
    // 💡 降维打击 3：不销毁对象，只是重置状态并把索引还给池子
    this.pool[nodeIndex].active = false;
    this.freeIndices.push(nodeIndex);
  }
}
```


# 主线程大逃亡 —— OffscreenCanvas
**业务场景：** 你做了一个极致复杂的 3D 渲染或者图表大屏。虽然你优化了渲染逻辑，但因为你的页面上还有庞大的 Vue/React 业务组件，当用户点击按钮触发 Vue 响应式 Diff 时，主线程依然被占满，导致 3D 动画卡顿。

- **菜鸟做法：** 用 `useMemo`, `v-once`, `requestIdleCallback` 在 Vue/React 里做极端的性能调优，试图在夹缝中求生存。
    
- **致命瓶颈：** 只要 JS 的 UI 渲染（DOM 操作）和 Canvas 绘制都在同一个**主线程**，它们就必定互相抢夺 CPU，永远无法彻底解决卡顿。
    
- **首席的降维打击（OffscreenCanvas）：** 前端只有主线程吗？错！ 我直接把 `<canvas>` 元素的控制权剥离，转移到后台隐藏的 **Web Worker 线程 (独立线程)**！ 主线程（Vue/React）**只负责监听用户的鼠标点击，然后通过 `postMessage` 把坐标发给 Worker。** 所有的矩阵计算、物理碰撞、画面绘制，全都在另一个 CPU 核心上狂奔。
    
- **核弹级效果：** 哪怕主线程里的 Vue 在进行极其庞大的万级列表 Diff，哪怕页面被业务逻辑卡死了 2 秒钟，你背景里的 Canvas 动画依然在另一个线程里以 60fps 完美运行，不受任何影响！

```ts
// 1. 获取 Canvas 的控制权
const canvas = document.getElementById('my-canvas');
// 💡 降维打击 1：剥夺主线程对 DOM Canvas 的渲染权！
const offscreen = canvas.transferControlToOffscreen(); 

// 2. 启动 Worker 后台线程
const worker = new Worker('render-worker.js');

// 3. 跨线程零拷贝转移！把画布的物理控制权直接扔给 Worker
worker.postMessage({ canvas: offscreen }, [offscreen]);

// Vue 组件只负责把用户的鼠标动作发过去
window.addEventListener('mousemove', (e) => {
  worker.postMessage({ type: 'MOUSE_MOVE', x: e.clientX, y: e.clientY });
});

// 此时，哪怕你写一个死循环 while(true) 把 Vue 卡死，Canvas 依然在流畅渲染！
```

# CPU 极致压榨 —— 读写分离拦截 (根治 Layout Thrashing)

```ts
const box1Width = box1.offsetWidth; // 读
box2.style.width = box1Width + 10 + 'px'; // 写
const box3Width = box3.offsetWidth; // 读
box4.style.width = box3Width + 10 + 'px'; // 写

// **首席的降维打击：** 引入 **FastDOM** 思想。封装一个拦截器，严禁在业务代码里随意读写 DOM。 把所有的“读”操作集中收集，所有的“写”操作集中收集。

// 把所有的“读”放一起
const w1 = box1.offsetWidth;
const w3 = box3.offsetWidth;
// 利用 requestAnimationFrame，把所有的“写”打包在下一帧一次性执行
requestAnimationFrame(() => {
  box2.style.width = w1 + 10 + 'px';
  box4.style.width = w3 + 10 + 'px';
});
```

# 渲染极致压榨 —— 一行 CSS 干翻“虚拟列表” (content-visibility)

- **菜鸟做法：** 发现页面 DOM 超过 5000 个，页面卡死。于是花 3 天时间引入 `vue-virtual-scroller` 或者 `react-window`，痛苦地改造数据结构，处理高度不固定的坑。
    
- **首席的降维打击：** 我根本不写虚拟列表，我只在这些长列表的容器或者复杂组件上加**一行 CSS**：
    
    CSS
    
    ```
    .heavy-component {
      content-visibility: auto;
      contain-intrinsic-size: 500px; /* 给一个预估高度防止滚动条乱跳 */
    }
    ```
    
- **王炸效果：** 浏览器引擎（Blink）接收到这个属性后，会**直接跳过屏幕可视区域之外所有 DOM 节点的 Layout（布局）和 Paint（绘制）计算！** 哪怕你的 HTML 里有 10 万个真实的 DOM 节点，只要它们没出现在屏幕上，渲染成本几乎为 0。你用 10 秒钟写一行 CSS，达到了别人重构 3 天的性能优化效果。

# 硬盘 I/O 压榨 —— 逃离 LocalStorage，拥抱 OPFS

**高频场景：** 在前端处理/缓存大文件（视频剪辑、Web Excel、SQLite 跑在浏览器里）。

- **菜鸟做法：** 把数据序列化成 JSON，硬塞进 `localStorage`。
    
- **致命隐患：** `localStorage` 最大只有 5MB 不说，它是一个**同步 API**。往里面写 2MB 数据，主线程就会卡顿几十毫秒。如果用 `IndexedDB`，它的底层封装又很厚，读写大文件依然很慢。
    
- **首席的降维打击：** 使用现代浏览器带来的终极存储核武器：**OPFS (Origin Private File System)**。
    
    JavaScript
    
    ``` ts
    // 获取沙盒文件系统根目录
    const root = await navigator.storage.getDirectory();
    // 创建并获取文件句柄
    const fileHandle = await root.getFileHandle('my_heavy_data.bin', { create: true });
    // 直接以文件流形式极速写入
    const writable = await fileHandle.createWritable();
    await writable.write(hugeDataBuffer);
    await writable.close();
    ```
    
- **王炸效果：** OPFS 绕过了浏览器传统的存储抽象层，直接在用户的硬盘上提供了一个高性能的、私有的沙盒文件系统。它的读写速度**直逼原生 C++ 桌面应用**。你可以把几十上百 MB 的数据毫无卡顿地瞬间刷入硬盘。


# 通信顺序进程 (CSP / Channel) —— 埋葬回调地狱

``` ts
// 1. 实现一个极简的 Channel 管道底层
class Channel {
  constructor() { this.queue = []; this.resolvers = []; }
  
  // 往管道里“倒水”
  put(val) {
    if (this.resolvers.length > 0) this.resolvers.shift()(val);
    else this.queue.push(val);
  }
  
  // 从管道里“抽水” (如果没有水，就阻塞等待！)
  take() {
    if (this.queue.length > 0) return Promise.resolve(this.queue.shift());
    return new Promise(resolve => this.resolvers.push(resolve));
  }
}

const ch = new Channel();

// 2. 消费者协程 (Goroutine)
async function consumer() {
  console.log('👀 消费者：我在等接口返回数据...');
  
  // 💡 降维打击：代码在这里“停住”了！就像 Go 语言的 data <- ch 
  // 没有任何的 .then() 或者回调函数嵌套！
  const data = await ch.take(); 
  
  console.log('✅ 消费者：拿到了！数据是:', data);
}

// 3. 生产者协程 (Goroutine)
async function producer() {
  console.log('⚙️ 生产者：去请求后端 API...');
  setTimeout(() => {
    console.log('⚙️ 生产者：数据回来了，塞进管道！');
    ch.put({ status: 200, user: 'John' }); 
  }, 2000);
}

// 启动！
consumer();
producer();
```

# 实体组件系统 (ECS) —— 榨干 CPU 缓存的终极形态

``` ts
// 假设画布上有 10 万个移动的粒子
const MAX_ENTITIES = 100000;

// ❌ 传统 OOP 做法：
// class Particle { x, y, vx, vy } 
// const particles = [new Particle(), new Particle()...]
// 悲剧：10 万个对象散落在内存各个角落，CPU 读取时频繁发生 Cache Miss（缓存未命中），巨卡。

// ✅ 降维打击 (Data-Oriented Design)：
// 彻底抛弃对象！直接向系统申请 4 块绝对连续的二进制内存！
const positionsX = new Float32Array(MAX_ENTITIES);
const positionsY = new Float32Array(MAX_ENTITIES);
const velocitiesX = new Float32Array(MAX_ENTITIES);
const velocitiesY = new Float32Array(MAX_ENTITIES);

// 初始化数据
for(let i = 0; i < MAX_ENTITIES; i++) {
  positionsX[i] = Math.random() * 800;
  velocitiesX[i] = 1.5;
  // ...
}

// 💡 灵魂系统 (System)：纯函数，毫无 this 的拖累
function movementSystem() {
  // 这个 for 循环的速度是极其恐怖的！
  // 因为 positionsX 是一段连续内存，CPU 会一次性把相邻的数据全部预读进 L1 缓存里！
  for (let i = 0; i < MAX_ENTITIES; i++) {
    positionsX[i] += velocitiesX[i];
    positionsY[i] += velocitiesY[i];
  }
}

// 游戏主循环
function loop() {
  movementSystem(); // 10万个粒子，毫秒级算完
  requestAnimationFrame(loop);
}
```

# Proxy 妙用

``` ts
// 💡 降维打击：创造一个没有任何实体方法，但能生成全宇宙 HTML 标签的魔法对象
const DOM = new Proxy({}, {
  // 拦截一切属性读取 (比如 DOM.div, DOM.h1)
  get(target, tagName) {
    // 返回一个函数，这个函数接收子节点
    return (...children) => {
      const el = document.createElement(tagName); // 根据你读取的属性名，创建真实 DOM
      
      for (const child of children) {
        if (typeof child === 'string') {
          el.appendChild(document.createTextNode(child));
        } else {
          el.appendChild(child); // 追加子元素
        }
      }
      return el;
    };
  }
});
```

 Saga：长流程编排

  核心思想：

  一个业务流程由多个异步步骤组成。
  中间失败时，要知道怎么补偿或回滚。

  适合场景：

  下单
  支付
  注册
  上传后生成预览
  创建项目后初始化配置
  前端多接口串联

  小 demo：

  ```ts
  async function runSaga(steps) {
    const completedSteps = [];

    try {
      for (const step of steps) {
        await step.do();
        completedSteps.push(step);
      }

      console.log('流程完成');
    } catch (error) {
      console.log('流程失败，开始补偿:', error.message);

      for (const step of completedSteps.reverse()) {
        if (step.undo) {
          await step.undo();
        }
      }
    }
  }

  runSaga([
    {
      do: async () => {
        console.log('1. 创建订单');
      },
      undo: async () => {
        console.log('撤销订单');
      },
    },
    {
      do: async () => {
        console.log('2. 扣库存');
      },
      undo: async () => {
        console.log('恢复库存');
      },
    },
    {
      do: async () => {
        console.log('3. 支付');
        throw new Error('支付失败');
      },
    },
  ]);
  ```

  function delay(ms) {
    return new Promise(resolve => setTimeout(resolve, ms));
  }

  async function runWorkflow(tasks, input, options = {}) {
    const concurrency = options.concurrency ?? 2;
    const names = Object.keys(tasks);

    const status = Object.fromEntries(names.map(name => [name, 'pending']));
    const results = {};
    const errors = {};
    const context = {
      input,
      results,
    };

    for (const name of names) {
      const deps = tasks[name].deps ?? [];

      for (const dep of deps) {
        if (!tasks[dep]) {
          throw new Error(`Task "${name}" depends on missing task "${dep}"`);
        }
      }
    }

    let runningCount = 0;

    return new Promise((resolve, reject) => {
      function markSkippedTasks() {
        let changed = false;

        for (const name of names) {
          if (status[name] !== 'pending') continue;

          const deps = tasks[name].deps ?? [];
          const hasBrokenDep = deps.some(dep => {
            return status[dep] === 'failed' || status[dep] === 'skipped';
          });

          if (hasBrokenDep) {
            status[name] = 'skipped';
            changed = true;
            console.log(`⏭️  SKIP ${name}`);
          }
        }

        if (changed) {
          markSkippedTasks();
        }
      }

      function getRunnableTask() {
        return names.find(name => {
          if (status[name] !== 'pending') return false;

          const deps = tasks[name].deps ?? [];
          return deps.every(dep => status[dep] === 'done');
        });
      }

      function isFinished() {
        return names.every(name => {
          return status[name] !== 'pending' && status[name] !== 'running';
        });
      }

      function schedule() {
        markSkippedTasks();

        if (isFinished()) {
          resolve({
            status,
            results,
            errors,
          });
          return;
        }

        while (runningCount < concurrency) {
          const name = getRunnableTask();

          if (!name) break;

          const task = tasks[name];
          status[name] = 'running';
          runningCount += 1;

          console.log(`▶️  RUN ${name}`);

          task
            .run(context)
            .then(result => {
              status[name] = 'done';
              results[name] = result;
              console.log(`✅ DONE ${name}`);
            })
            .catch(error => {
              status[name] = 'failed';
              errors[name] = error;
              console.log(`❌ FAIL ${name}: ${error.message}`);
            })
            .finally(() => {
              runningCount -= 1;
              schedule();
            });
        }

        const hasRunnable = Boolean(getRunnableTask());
        const hasPending = names.some(name => status[name] === 'pending');

        if (runningCount === 0 && hasPending && !hasRunnable) {
          reject(new Error('Workflow is stuck. Check for circular dependencies.'));
        }
      }

      schedule();
    });
  }

› 还是有点不懂， status 有什么值，分别代表什么。怎么判断是否能够并行？


• status 可以理解成调度器给每个任务贴的执行状态。这个 demo 里有 5 种：

  pending   // 还没开始，正在等依赖
  running   // 正在执行
  done      // 执行成功
  failed    // 执行失败
  skipped   // 因为依赖失败，所以自己不执行了

  比如任务图是：

  A: validateArticle
  B: compressCover
  C: uploadCover      依赖 B
  D: saveDraft        依赖 A
  E: publishArticle   依赖 C + D
  F: refreshList      依赖 E

  初始状态：

  {
    validateArticle: 'pending',
    compressCover: 'pending',
    uploadCover: 'pending',
    saveDraft: 'pending',
    publishArticle: 'pending',
    refreshList: 'pending',
  }

  怎么判断一个任务能不能跑？

  核心规则就一句：

  > 一个任务的所有依赖都是 done，它就可以跑。

  代码对应这里：

  const deps = tasks[name].deps ?? [];
  return deps.every(dep => status[dep] === 'done');

  比如：

  uploadCover: {
    deps: ['compressCover'],
  }

  那只有当：

  status.compressCover === 'done'

  uploadCover 才能执行。

  再比如：

  publishArticle: {
    deps: ['uploadCover', 'saveDraft'],
  }

  那必须同时满足：

  status.uploadCover === 'done'
  status.saveDraft === 'done'

  publishArticle 才能执行。

  怎么判断是否能够并行？

  也是一句话：

  > 当前有多个任务都满足“依赖已完成”，它们之间又互不依赖，就可以并行。

  比如一开始：

  validateArticle 没有依赖
  compressCover 没有依赖

  所以它俩都能立刻跑：

  validateArticle  running
  compressCover    running

  如果 concurrency = 2，最多同时跑 2 个，所以这两个一起跑。

  等 validateArticle 完成后：

  saveDraft 依赖 validateArticle
  generateSummary 依赖 validateArticle

  这两个也可以并行，因为它们都只依赖已经完成的 validateArticle，彼此之间没有依赖关系。

  saveDraft       running
  generateSummary running

  但是 publishArticle 不能并行提前跑，因为它依赖：

  uploadCover + saveDraft

  只要其中一个没完成，它就还是：

  publishArticle: 'pending'

  举个时间线

  假设并发数是 2：

  第 0 秒：
  validateArticle 可以跑
  compressCover 可以跑
  => 两个并行

  第 0.3 秒：
  validateArticle done
  saveDraft 可以跑
  generateSummary 可以跑
  但 concurrency = 2，此时 compressCover 还在跑
  => 只能再启动一个，比如 saveDraft

  第 0.8 秒：
  compressCover done
  uploadCover 可以跑
  => 启动 uploadCover

  第 0.9 秒：
  saveDraft done
  generateSummary 可以跑
  => 启动 generateSummary

  第 1.8 秒：
  uploadCover done
  但 publishArticle 还要等 saveDraft
  saveDraft 已经 done
  => publishArticle 可以跑

  publishArticle done 后：
  refreshList 和 sendNotification 都可以跑
  => 并行

  重点是：不是程序员手动决定谁并行，而是调度器根据 deps 和 status 算出来。

  你可以把它想成这个公式：

  可执行任务 = pending 任务中，所有 deps 都是 done 的任务
  可并行任务 = 同一轮里多个可执行任务
  实际并行数量 = min(可执行任务数量, concurrency 剩余名额)

  所以 DAG Workflow 的核心不是 status 本身，而是：

  用 status 记录每个任务进度
  用 deps 判断任务是否解锁
  用 concurrency 控制最多同时跑几个

# Actor Model：每个对象都有自己的邮箱

  核心思想：

  不要直接改别人的状态。
  给它发消息，让它自己处理。

  很像 Channel，但区别是：Channel 是一根管道，Actor 是带状态的独立小系统。

  适合场景：

  聊天窗口
  Web Worker
  多人协作
  游戏角色
  每个 Tab / 每个会话独立管理

  小 demo：
```ts

  function createActor(initialState, reducer) {
    let state = initialState;
    const mailbox = [];

    async function loop() {
      while (true) {
        const message = mailbox.shift();

        if (message) {
          state = reducer(state, message);
          console.log('state:', state);
        }

        await new Promise(resolve => setTimeout(resolve, 0));
      }
    }

    loop();

    return {
      send(message) {
        mailbox.push(message);
      },
      getState() {
        return state;
      },
    };
  }

  const counterActor = createActor(0, (state, message) => {
    if (message.type === 'inc') return state + 1;
    if (message.type === 'dec') return state - 1;
    return state;
  });

  counterActor.send({ type: 'inc' });
  counterActor.send({ type: 'inc' });
  counterActor.send({ type: 'dec' });

  业务理解：

  组件不要直接 set 某个复杂对象。
  而是 send({ type: 'xxx' })，让那个对象自己决定怎么变。

  前端里 Zustand、Redux、XState、Web Worker 通信里都有 Actor 思想。
```

```ts
function createActor(initialState, handler) {
    let state = initialState;
    const mailbox = [];
    let running = false;

    async function process() {
      if (running) return;

      running = true;

      while (mailbox.length > 0) {
        const message = mailbox.shift();

        try {
          const result = await handler(state, message);
          state = result.state;

          if (message.reply) {
            message.reply.resolve(result.reply);
          }
        } catch (error) {
          if (message.reply) {
            message.reply.reject(error);
          } else {
            console.error('actor error:', error.message);
          }
        }
      }

      running = false;
    }

    return {
      send(type, payload) {
        mailbox.push({ type, payload });
        process();
      },

      ask(type, payload) {
        return new Promise((resolve, reject) => {
          mailbox.push({
            type,
            payload,
            reply: { resolve, reject },
          });

          process();
        });
      },

      getState() {
        return state;
      },
    };
  }

  const cartActor = createActor(
    { items: [] },
    async (state, message) => {
      if (message.type === 'add') {
        return {
          state: {
            items: [...state.items, message.payload],
          },
        };
      }

      if (message.type === 'count') {
        return {
          state,
          reply: state.items.length,
        };
      }

      return { state };
    },
  );

  cartActor.send('add', { id: 1, name: 'Book' });
  cartActor.send('add', { id: 2, name: 'Pen' });

  cartActor.ask('count').then(count => {
    console.log('cart count:', count);
  });

  适合：聊天会话、WebSocket 连接、播放器、购物车、每个 Tab 独立业务单元。
```

# Outbox：可靠副作用队列
  用户操作先入队，worker 慢慢发，失败后重试。
``` ts

  const outbox = [];

  function enqueue(text) {
    outbox.push({
      id: Date.now(),
      text,
      status: 'queued',
      attempts: 0,
    });
  }

  async function sendToServer(item) {
    await sleep(500);

    if (Math.random() < 0.5) {
      throw new Error('network error');
    }

    console.log('sent:', item.text);
  }

  async function outboxWorker() {
    while (true) {
      const item = outbox.find(x => x.status === 'queued' || x.status === 'failed');

      if (!item) {
        await sleep(300);
        continue;
      }

      item.status = 'sending';
      item.attempts += 1;

      try {
        await sendToServer(item);
        item.status = 'sent';
      } catch (error) {
        item.status = 'failed';
        console.log('retry later:', item.text);
        await sleep(1000);
      }
    }
  }

  function sleep(ms) {
    return new Promise(resolve => setTimeout(resolve, ms));
  }

  enqueue('hello');
  enqueue('world');

  outboxWorker();

  适合：聊天发送、埋点、草稿同步、离线提交。
```

# Circuit Breaker 熔断器

```ts
function createCircuitBreaker(fn, options) {
    let state = 'closed';
    let failures = 0;
    let openedAt = 0;

    return async function run() {
      const now = Date.now();

      if (state === 'open') {
        if (now - openedAt < options.cooldown) {
          throw new Error('circuit open');
        }

        state = 'half-open';
        console.log('state: half-open');
      }

      try {
        const result = await fn();

        failures = 0;
        state = 'closed';
        return result;
      } catch (error) {
        failures += 1;

        if (failures >= options.maxFailures) {
          state = 'open';
          openedAt = Date.now();
          console.log('state: open');
        }

        throw error;
      }
    };
  }

  async function unstableApi() {
    await sleep(300);

    if (Math.random() < 0.8) {
      throw new Error('api failed');
    }

    return 'ok';
  }

  function sleep(ms) {
    return new Promise(resolve => setTimeout(resolve, ms));
  }

  const api = createCircuitBreaker(unstableApi, {
    maxFailures: 3,
    cooldown: 2000,
  });

  setInterval(() => {
    api()
      .then(result => console.log('success:', result))
      .catch(error => console.log('error:', error.message));
  }, 500);

  适合：第三方接口、AI 接口、短信、支付、地图服务。
```

# SWR：Stale While Revalidate
```ts
const cache = new Map();

  async function swr(key, fetcher, onUpdate) {
    if (cache.has(key)) {
      const oldData = cache.get(key);
      console.log('return stale:', oldData);
      revalidate(key, fetcher, onUpdate);
      return oldData;
    }

    const freshData = await fetcher();
    cache.set(key, freshData);
    return freshData;
  }

  async function revalidate(key, fetcher, onUpdate) {
    const freshData = await fetcher();
    cache.set(key, freshData);
    console.log('fresh:', freshData);
    onUpdate(freshData);
  }

  async function fetchUser() {
    await sleep(800);

    return {
      name: 'John',
      updatedAt: new Date().toLocaleTimeString(),
    };
  }

    return new Promise(resolve => setTimeout(resolve, ms));

  swr('user', fetchUser, data => {
    console.log('ui update:', data);
  }).then(data => {
    console.log('first render:', data);
  });

  setTimeout(() => {
    swr('user', fetchUser, data => {
```

# Supervisor Tree：监督树

长期任务失败后，由 supervisor 决定是否重启.

```ts
function createSupervisor(workers) {
    const restartCount = {};

    for (const worker of workers) {
      restartCount[worker.name] = 0;
      startWorker(worker);
    }

    async function startWorker(worker) {
      try {
        console.log('start:', worker.name);
        await worker.run();
      } catch (error) {
        restartCount[worker.name] += 1;

        console.log(
          'crashed:',
          worker.name,
          error.message,
          'restart:',
          restartCount[worker.name],
        );

        if (restartCount[worker.name] > worker.maxRestarts) {
          console.log('stop permanently:', worker.name);
          return;
        }

        setTimeout(() => {
          startWorker(worker);
        }, worker.restartDelay);
      }
    }
  }

  function createUnstableWorker(name) {
    return {
      name,
      maxRestarts: 3,
      restartDelay: 1000,

      async run() {
        let count = 0;

        while (true) {
          await sleep(500);
          count += 1;

          console.log(name, 'tick', count);

          if (Math.random() < 0.3) {
            throw new Error('worker failed');
          }
        }
      },
    };
  }

  function sleep(ms) {
    return new Promise(resolve => setTimeout(resolve, ms));
  }

  createSupervisor([
    createUnstableWorker('websocket-worker'),
    createUnstableWorker('outbox-worker'),
  ]);

  一个 worker 挂了，只重启它，不影响另一个。

  适合：WebSocket、轮询、Outbox worker、后台同步、音视频连接。
```

# Backpressure：背压
```ts
 2. Backpressure：背压

  正规一点的背压不是“丢”，而是：

  队列满了，producer 的 put 会等待
  consumer 消费掉一个位置后，producer 才能继续放

  这才是真正的“反压”。

  class BoundedChannel {
    constructor(capacity) {
      this.capacity = capacity;
      this.queue = [];
      this.takers = [];
      this.putters = [];
    }

    async put(value) {
      if (this.takers.length > 0) {
        const taker = this.takers.shift();
        taker(value);
        return;
      }

      if (this.queue.length < this.capacity) {
        this.queue.push(value);
        return;
      }

      await new Promise(resolve => {
        this.putters.push({ value, resolve });
      });
    }

    async take() {
      if (this.queue.length > 0) {
        const value = this.queue.shift();

        if (this.putters.length > 0) {
          const putter = this.putters.shift();

          if (this.takers.length > 0) {
            const taker = this.takers.shift();
            taker(putter.value);
          } else {
            this.queue.push(putter.value);
          }

          putter.resolve();
        }

        return value;
      }

      return new Promise(resolve => {
        this.takers.push(resolve);
      });
    }
  }

  function sleep(ms) {
    return new Promise(resolve => setTimeout(resolve, ms));
  }

  const channel = new BoundedChannel(3);

  async function producer() {
    for (let i = 1; i <= 10; i += 1) {
      console.log('try put:', i);
      await channel.put(i);
      console.log('put ok:', i);
    }
  }

  async function consumer() {
    while (true) {
      const item = await channel.take();
      console.log('consume:', item);
      await sleep(1000);
    }
  }

  producer();
  consumer();

  这里不会丢任务。
  当队列满了，producer 会卡在：

  await channel.put(i);

  这就是背压：

  消费者慢 -> 队列满 -> 生产者被迫慢下来

  适合：上传队列、离线同步、消息发送、批量导入。
```
