学习了使用 Docker 横向扩容订单服务。多个订单 API 实例共享同一个数据库，并且不依赖进程内存保存业务状态，因此任意实例都可以处理请求。

然后了解了订单已经保存成功，但同步调用通知服务失败时，会出现“订单已保存、通知未完成，而 API 可能返回失败”的部分失败问题。

接着使用 RabbitMQ，将“订单已创建”事件发布到队列，再由通知 Worker 异步消费。这样即使通知 Worker暂时不可用，消息也会保留在 RabbitMQ 中；订单 API 不需要等待通知处理完成。

但这又产生了一个问题：如果订单已经写入数据库，而向 RabbitMQ 发布事件时 RabbitMQ 恰好不可用，就会出现“订单已经存在，但对应事件没有成功发布”的不一致。

这时可以使用 Transactional Outbox。它的本质是增加一张 `outbox_events` 表，在同一个数据库事务中同时写入订单记录和待发布事件。之后由独立的 `outbox-relay` 查询 `published_at IS NULL` 的待发布事件，将其发送到 RabbitMQ，并在发送成功后更新 `published_at`。

``` ts
// `outbox-relay` 可以翻译成“Outbox 转发器”。
// 它是一个独立运行的后台 Node.js 程序，职责只有一个：
// 把 PostgreSQL `outbox_events` 表里的待发布事件转发到 RabbitMQ。

// 运行逻辑相当于：
// 
// 不断查询 outbox_events
//         ↓
// 找到 published_at IS NULL 的事件
//         ↓
// 发布到 RabbitMQ
//         ↓
// 等待 RabbitMQ Confirm
//         ↓
// 把 published_at 更新为当前时间


// 伪代码就是：

while (true) {
  const event = await findPendingOutboxEvent()

  if (event) {
    await publishToRabbitMQ(event)
    await markAsPublished(event.id)
  }
}

```


RabbitMQ 保证一条消息至少有机会被消费一次，但同一条消息可能被投递多次。

正常流程：
```
RabbitMQ 把 E1001 交给 Worker
Worker 写入 notifications
Worker 返回 ACK
RabbitMQ 删除消息
```

异常流程：
```
1. RabbitMQ 把 E1001 交给 Worker
2. Worker 成功写入 notifications
3. Worker 还没发送 ACK 就崩溃
4. RabbitMQ 没收到 ACK
5. RabbitMQ 把 E1001 重新放回队列
6. 新 Worker 再次收到 E1001
```

于是同一个 ID被投递了两次：

```
第一次收到：eventId = E1001
第二次收到：eventId = E1001
```


**Outbox 也可能重复发布**：
```
1. Relay 把 eventId=E1001 发布到 RabbitMQ
2. RabbitMQ Confirm 成功
3. Relay 还没更新 published_at 就崩溃
4. Relay 恢复后仍看到 published_at IS NULL
5. Relay 再次发布 eventId=E1001
```

这时 RabbitMQ 里可能真的出现两条具有相同 `eventId` 的消息。

**消费者增加一张表**：
```
processed_events
----------------
event_id 主键
processed_at
```

消费时：
```
BEGIN

检查 processed_events 是否存在 E1001

如果不存在：
  写入 processed_events(E1001)
  写入 notifications

如果已经存在：
  什么都不做

COMMIT
ACK


const inserted = await tryInsertProcessedEvent(eventId)

if (inserted) {
  await createNotification()
}

// 无论是首次处理还是重复消息，成功后都 ACK
channel.ack(message)
```

还有：
rabbitMQ 分3种队列：

notification.order-created.v2
正常消费队列

notification.order-created.retry.v2
失败后等待 1 秒的重试队列

notification.order-created.dlq.v2
多次失败后的死信队列
